# Concurrency and Resource Management

Trash-compactor keeps the parts of the workload that benefit from true parallelism in native code while the parts that are naturally serial or subprocess-bound stay in Python. The split lets the program use all the cores it can without fighting the GIL or thrashing the disk.

## Worker Sizing

CPU information comes from `src/config.py`. The baseline for scan and entropy work is "physical cores minus one" (or one on very small machines). Environment variables and a context-var cap let callers or tests reduce that number when desired.

Compression workers are chosen differently by algorithm:

- XPRESS variants are cheap enough that one worker per logical core (minus a spare) is fine.
- LZX is capped at two concurrent workers on machines with more than four cores, and one on smaller systems, since LZX compression itself is multi-threaded rather than single-threaded.

Scan and entropy worker counts feed directly into the Rust extension as `scan_worker_count` and `entropy_worker_count`.

## Drive Type Considerations

For compressing data on spinning hard drives, serial single-threaded compression is preferred. The `-s` flag (or GUI "Slow HDD mode) forces a single worker for everything that touches the drive, since concurrent random writes on HDDs produce both terrible throughput and extra fragmentation.

Drive detection (in drive_inspector) uses seek penalty IOCTL + MSFT_PhysicalDisk (MediaType=3 for HDD, SpindleSpeed) + PS Get-PhysicalDisk fallback + fallbacks for better coverage of NVMe/eMMC.

SSD and NVMe drives do not have this restriction, so the full core count is used.

## The Native Parallel Layer

The two most expensive phases on large trees—full directory walking with classification, and entropy sampling—are no longer performed with Python threads or processes. They run inside the `fast_walk` Rust crate using rayon.

`walk_and_filter` walks the tree with a small pool of native threads. Work is distributed with a shared stack protected by a mutex and a pending counter; each thread pulls directories, emits classified file batches, and pushes newly discovered subdirectories. Because everything happens outside the Python interpreter, there is no GIL contention on the syscall and path-manipulation hot paths. The result is sustained throughput in the tens of thousands of files per second even while Python is still formatting progress messages.

Entropy probing (`probe_directories_parallel`) similarly farms independent directories out with rayon. Inside a directory the largest files are chosen, multiple windows are read (mmap for files above a couple of megabytes), and the LZ4-then-zlib probe runs. The only Python objects that cross the boundary are the final aggregated results and an optional progress callback. This is why entropy analysis stayed fast even after the window count became dynamic for large files.

## Compression Execution

The actual NTFS compression step still uses Python `ThreadPoolExecutor` to launch batches of `compact.exe`. Each batch is a single subprocess invocation covering up to a hundred files or the Windows command-line length limit, whichever comes first. Python's role here is mostly waiting; the threads exist only to keep several compact processes in flight. The executor groups work by algorithm so that the more expensive LZX batches can be rate-limited independently of the quick XPRESS ones.

The net effect is that the GIL-sensitive or allocation-heavy phases have been moved to native code where they belong, while the parts that must talk to an external tool remain simple Python orchestration.
