# Concurrency and Resource Management

Trash-compactor keeps the parts of the workload that benefit from true parallelism in native code while the parts that are naturally serial or subprocess-bound stay in Python. The split lets the program use all the cores it can without fighting the GIL or thrashing the disk.

## Worker Sizing

The baseline for scan and entropy work is "physical cores minus one" (or one on very small machines). Environment variables and a runtime cap can lower that number.

Compression workers are chosen differently by algorithm:

- XPRESS variants are cheap enough that one worker per logical core (minus a spare) is fine.
- LZX is capped at two concurrent workers on machines with more than four cores, and one on smaller systems. LZX compression itself is multi-threaded.

Scan and entropy worker counts feed directly into the Rust extension.

## Drive Type Considerations

For compressing data on spinning hard drives, serial single-threaded compression is preferred. The `-s` flag (or GUI "Slow HDD mode") forces a single worker for everything that touches the drive. Concurrent random writes on HDDs produce both terrible throughput and extra fragmentation.

Drive detection uses seek-penalty IOCTL, then MSFT_PhysicalDisk (MediaType 3 is HDD), then PowerShell Get-PhysicalDisk, then metadata heuristics.

SSD and NVMe drives do not have this restriction. They use the full core count.

## The Native Parallel Layer

The two most expensive phases on large trees, walking with classification and entropy sampling, are no longer performed with Python threads or processes. They run inside the `fast_walk` crate using rayon.

The walker uses a small pool of native threads. Work is distributed with a shared stack protected by a mutex and a pending counter. Each thread pulls directories, emits classified file batches, and pushes newly discovered subdirectories. Because everything happens outside the Python interpreter, there is no GIL contention on the syscall and path-manipulation hot paths. The result is sustained throughput in the tens of thousands of files per second even while Python is still formatting progress messages.

Entropy probing similarly farms independent directories out with rayon. Inside a directory the largest files are chosen on the fly during a single walk. A bounded selection keeps only the largest N candidates, and a full per-directory file list is never materialised. Multiple windows are read (mmap for files above a couple of megabytes), then the LZ4-then-zlib probe runs. Python only sees the aggregated scores.

## Compression Execution

The actual NTFS compression step still launches batches of `compact.exe` from Python. Each batch is a single subprocess invocation covering up to a hundred files or the Windows command-line length limit, whichever comes first. Python's role here is mostly waiting. The threads exist only to keep several compact processes in flight. The executor groups work by algorithm. The more expensive LZX batches can be rate-limited independently of the quick XPRESS ones.
