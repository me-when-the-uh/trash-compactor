# Native Acceleration

The core scanning and entropy work moved into a small Rust crate (`fast_walk`) exposed to Python through PyO3. The change was driven by a simple observation: directory walking and sampling are dominated by syscalls, path manipulation, and small compression probes. Python's interpreter overhead and the GIL made it hard to use all the cores without fighting the language.

## What the Extension Does

Two functions are the public surface:

- `walk_and_filter` performs a parallel tree walk. It classifies every file (extension, size, already-compressed) and obtains the NTFS on-disk size hint in the same pass. Results arrive in batches so callers can stream them without buffering an entire multi-gigabyte tree.
- `probe_directories_parallel` runs the entropy sampling plan for many directories at once. It re-uses the same "pick the largest N files" selection, dynamic window counts, LZ4 fast path, and zlib level-2 probe that the pure-Python version used, but now those probes run on rayon threads with mmap for anything big enough to benefit.

Both are gated by the environment variable `TRASH_COMPACTOR_USE_FAST_WALK` (default on) and are required for normal operation; the pure-Python fallbacks have been removed from the main paths.

## Why It Is Fast

A few design choices compound:

The walk avoids allocating a Python object per file or per directory entry during the hot loop. Only small batches of plain tuples cross the FFI boundary. Inside Rust the work is stolen across a pool of threads using rayon's scope and a simple pending-counter protocol; newly discovered subdirectories are pushed back onto the shared work list with almost no Python involvement.

Entropy work benefits from the same thread pool plus two cheap wins. First, LZ4 is used as a gate: many real-world incompressible files (already-compressed archives, media, etc.) are rejected after a few microseconds instead of paying for a full zlib round. Second, files above a couple of megabytes are memory-mapped so the kernel does the paging and the probe never issues a second read syscall for the same data.

Because these phases no longer hold the GIL for long, the Python side can continue to update timers, check for cancellation, and feed the GUI without artificial serialisation. The measured effect on large trees is both higher absolute throughput and lower RAM residency, since the streaming batches replace the old full-materialisation lists.

## Interaction With the Rest of the Program

Worker counts for the native pools come from the same CPU-topology logic that used to size Python pools (`entropy_worker_count`, `scan_worker_count`). The single-worker (`-s`) and LZX-throttling rules still apply; they simply reduce the rayon thread count instead of the Python executor size.

The incompressible cache and all the stats recording stay in Python. Rust only ever returns raw numbers and paths; the policy decisions ("is 12 % savings good enough?") and the persistent `.db` file are handled on the Python side exactly as before.

The PyInstaller hooks and runtime preload make sure the native module is present and importable inside a frozen one-file executable. Diagnostic output under `TRASH_COMPACTOR_DIAGNOSTIC=1` prints whether the extension was loaded so that packaging problems are obvious.

In short, the Rust module is not a rewrite of the whole tool. It is a targeted extraction of the two loops that were measurably limited by Python, leaving the higher-level policy, UI, and `compact.exe` orchestration where they are easy to change in Python.
