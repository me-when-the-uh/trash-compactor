# Native Acceleration

The core scanning and entropy work resides in a small Rust crate (`fast_walk`) exposed to Python through PyO3. Having Rust instead of Python helps dramatically improve directory walking and sampling performance, because those are dominated by syscalls, path manipulation, and small compression probes. Python's interpreter overhead and the GIL made it hard to use all the cores without fighting the language.

## What the Extension Does

- `walk_and_filter` performs a parallel tree walk. It classifies every file (extension, size, already-compressed check) and obtains the NTFS on-disk size hint. Results arrive in batches so callers can stream them without buffering an entire multi-gigabyte tree.
- `probe_directories_parallel` runs the entropy sampling plan for many directories at once. It selects the largest N files, dynamic window counts, LZ4 fast path, and zlib level-2 probe, all of which used to be performed with the prior pure-Python versions, but the core change with Rust acceleration is that it's all run on rayon threads with mmap for anything big enough to benefit. The largest-N selection is folded into a single walk with a bounded candidate list to save memory for 1M+ files in the scanned directories. Per-directory sampled path lists are optional and off by default.

Both are gated by the environment variable `TRASH_COMPACTOR_USE_FAST_WALK` (on by default) and are required for normal operation. A pure-Python serial entropy fallback still exists (`evaluate_entropy_directory` / `sample_directory_entropy`) and is used for single-worker runs, small trees, and HDD mode; it applies the same sampling budgets as the native path so results agree.

## Why It Is Fast

A few design choices compound:

The walk avoids allocating a Python object per file or per directory entry during the hot loop. Only small batches of plain tuples cross the FFI boundary. Inside Rust the work is stolen across a pool of threads using rayon's scope and a simple pending-counter protocol, and newly discovered subdirectories are pushed back onto the shared work list.

Entropy work benefits from the same thread pool plus two cheap wins. First, LZ4 is used as a gate: many real-world incompressible files (already-compressed unclassified archives, media, etc.) are rejected after a few microseconds instead of paying for a full zlib round. Second, files above a couple of megabytes are memory-mapped so the kernel does the paging and the probe never issues a second read syscall for the same data.

Python side handles updating timers, check for cancellation, and feed the GUI without artificial serialisation. The measured effect on large trees is both higher absolute throughput and lower RAM residency, since the streaming batches replace the old full-materialisation lists.

## Interaction With the Rest of the Program

Worker counts for the native pools come from the same CPU-topology logic that used to size Python pools (`entropy_worker_count`, `scan_worker_count`). The single-worker (`-s`) and LZX-throttling rules still apply; they simply reduce the rayon thread count instead of the Python executor size.

The incompressible cache and all the stats recording stay in Python. Rust only ever returns raw numbers and paths; the policy decisions ("is 12 % savings good enough?") and the persistent `.db` file are handled on the Python side exactly as before.

The PyInstaller hooks and runtime preload make sure the native module is present and importable inside a frozen one-file executable. Diagnostic output under `TRASH_COMPACTOR_DIAGNOSTIC=1` prints whether the extension was loaded so that packaging problems are obvious.
