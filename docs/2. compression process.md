# Compression Execution

The execution phase transforms the compression plan (a list of file paths and their assigned algorithms) into on-disk changes.

## Orchestration

The executor accepts the plan and a set of worker constraints. Instead of processing files strictly in order, it groups them by algorithm (XPRESS4K, XPRESS8K, XPRESS16K, LZX). This grouping allows the program to apply different concurrency limits to different algorithms.

## Batch Processing

The executor processes files in batches rather than individually. A batch is formed when it reaches either 100 files or when the combined command-line length approaches the 4000-character limit imposed by Windows.

For each batch, a single command line is built for the Windows Compact utility: `compact /c /a /exe:<algorithm> <file1> <file2> ...`. The command runs with the console window hidden to prevent UI flashing.

Each `compact.exe` invocation is bounded by a timeout. A batch waits at least ten minutes and a single file at least one minute. `compact.exe` is taken from System32 when that copy exists, and its text is read in the console code page. Stopping a run ends `compact.exe` processes that have already started.

## Verification and Fallback

After a batch completes, the program confirms whether or not a file has been compressed successfully.

That check uses the Windows API `GetCompressedFileSizeW` to retrieve the actual on-disk size, compared against the logical file size. If the on-disk size is smaller, the compression is deemed successful.

If a batch operation fails (indicated by a non-zero exit code from `compact.exe`) or if an exception occurs, the program assumes that one or more files in the batch caused the issue. It then verifies which files in that batch went through and retries only the rest. The retries use the same worker pool.

When the failure text is "The file system does not support compression" on a volume already known to be NTFS, the executor logs a dedicated message once per volume suggesting `fltmc attach Wof X:` (the WOF minifilter is not attached).

If `compact.exe` instead reports a BypassIO veto (the game has the file open on the fast path), the file is skipped and remaining files in the same directory are not retried. The skip is recorded and the file is not counted as compressed. DirectStorage trees are normally already gone from the plan. This is the safety net for a title that is running or whose runtime DLL was missed.

A file that fails every attempt is counted as a failure and listed under the run's errors. The process exits 1 when that list is not empty. A BypassIO skip is not a failure.

A volume that reports "The file system does not support compression" is latched after the first such batch. The batch is verified, files that are not compressed are counted as skipped with a dedicated reason, and later batches and retries on that volume are skipped without starting `compact.exe`. One error per volume names `fltmc attach Wof X:` as the workaround.

Paths at MAX_PATH (260 characters) never reach this stage. They are filtered during planning because `compact.exe` rejects them with "Out of memory." even when the path itself is otherwise usable.
