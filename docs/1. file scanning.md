# File Scanning

Trash-compactor identifies compressible files through discovery, filtering, and planning. The flow begins when a directory is handed to the compression machinery and is designed to be fast enough for interactive use even on very large trees.

Discovery is handled by `iter_files` in `src/compression/file_scan.py`. It relies on the native `fast_walk` extension (written in Rust) to walk the tree. The Rust walker yields categorized entries in batches and is now the required implementation.

## Discovery

The native walker receives the root, a list of excluded directories, skip extensions, size thresholds, and a worker count. It performs the recursive walk, extension-based filtering, minimum-size checks, and NTFS compressed-size probes all in native code. Results stream back to Python as small batches so the GUI and progress reporting can stay responsive without materializing the entire tree in memory.

Static directory exclusions (system folders such as Windows, $Recycle.Bin, and so on) are applied inside the walker using normalized path prefix matching. This early cut avoids descending into areas that must never be touched. Dynamic high-entropy directory pruning during the walk itself is no longer performed for the main scan; the walk is fast enough that it is simpler and more accurate to discover candidates first and then apply entropy filtering to the collected set.

## Planning

`plan_compression` in `src/compression/compression_planner.py` receives the stream of entries and builds the final list of work.

Classification for eligibility (extension, size, already-compressed) now happens inside the Rust walker using the same logic that used to live in Python helpers. The returned tuples already carry the chosen algorithm index, a category code, and a size hint from `GetCompressedFileSizeW`.

### Algorithm Selection

Size thresholds from `src/config.py` decide the NTFS algorithm before any I/O:

- below 64 KiB: XPRESS4K
- 64–256 KiB: XPRESS8K
- 256 KiB–1 MiB: XPRESS16K
- 1 MiB and up: LZX (subject to the runtime benchmark that may disable it on slow CPUs)

This mapping is done with a simple cumulative threshold count so the decision is just an integer that the executor later turns into the right `/exe:` flag.

### Post-Discovery Entropy Filtering

After the walk finishes, `_filter_high_entropy_directories` groups the remaining candidates by parent directory and runs entropy sampling on whole directories. Any directory whose projected savings fall below the configured minimum is dropped in bulk, together with all of its files. This is the main place where "should we bother?" decisions are made after the cheap structural filters have run.

A root-level entropy sample is also taken when the target directory itself contains compressible-looking files; the result can cause the entire run to be skipped early.

## Entropy Sampling

The goal of entropy sampling is to decide, without writing anything and without reading every byte, whether compressing a directory tree is likely to be worthwhile. The implementation lives in both a small Python wrapper (`src/compression/entropy.py`) and a high-performance reimplementation inside the Rust `fast_walk` crate.

File selection inside a directory is deterministic and biased toward impact: the walker collects candidate files, sorts them by descending size, and keeps only the largest N (default 50, controlled by `TRASH_COMPACTOR_ENTROPY_MAX_FILES`). Largest files dominate the potential space savings, so focusing the sampling budget there produces more reliable projections than uniform random sampling would.

For each chosen file a number of sample windows are read. The count is not fixed at three. Small files (2 MiB and below) receive the base of three windows. Larger files receive progressively more windows, scaling from four up to a hard maximum of twenty once the file reaches 100 MiB. The extra samples on big files reduce the chance that a large incompressible blob fools the estimator into thinking the whole directory is compressible. Each window is nominally 16 KiB; the implementation merges overlaps and respects a per-directory byte budget so total I/O stays bounded.

Window placement for the three-window case targets roughly the 10 %, 45 %, and 80 % marks. This deliberately steps over the headers and trailers that many media and archive formats leave uncompressed. For files that use more windows the positions are spread evenly.

Each sample is first offered to LZ4. If LZ4 reports that the block is almost incompressible (ratio ≥ 0.95), the probe returns immediately with an entropy of 8.0 and marks the chunk as "certainly incompressible". Only when LZ4 does not short-circuit does the code fall back to zlib at level 2. Level 2 was chosen because it matches the compression style of the NTFS algorithms closely enough for good savings estimates while remaining fast. The weighted average entropy across the bytes actually read becomes the directory's score.

Directory probes themselves run in parallel through `probe_directories_parallel` exposed by the Rust module. Rayon distributes the independent directory plans across threads; inside each plan the per-file probes can also exploit parallelism for the larger jobs. Python only sees the aggregated `DirEntropyResult` records. The older `ProcessPoolExecutor` path remains as a fallback for serial or single-worker cases.

A persistent `IncompressibleCache` (backed by xxhash64 of absolute paths) lets the program remember directories it has already declared high-entropy on previous runs. When a hit occurs the expensive sampling step is skipped entirely.

Finally `savings_from_entropy` turns the average entropy value (0–8 bits per byte) into a projected percentage saving that the rest of the UI and reporting use.

## Execution

Once planning is complete the resulting list of (path, size, algorithm) tuples is handed to the executor. Worker counts for compression are still chosen from the Python side according to CPU topology and drive type (see the concurrency notes), but the heavy lifting of discovery and entropy has moved into native code.
