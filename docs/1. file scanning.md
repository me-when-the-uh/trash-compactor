# File Scanning

Trash-compactor identifies compressible files through discovery, filtering, and planning. The flow begins when a directory is handed to the compression machinery and is designed to be fast enough for interactive use even on very large trees.

Discovery relies on the native `fast_walk` extension (written in Rust) to walk the tree. The walker yields categorized entries in batches and is the required implementation.

## Discovery

The native walker receives the root, a list of excluded directories, skip extensions, size thresholds, and a worker count. It performs the recursive walk, extension-based filtering, minimum-size checks, and NTFS compressed-size probes all in native code. Results stream back to Python as small batches. The GUI and progress reporting stay responsive without materializing the entire tree in memory.

Static directory exclusions (system folders such as Windows, $Recycle.Bin, and so on) are applied inside the walker using normalized path prefix matching. User directory prefixes can also be defined in `%APPDATA%\TrashCompactor\exclusions.txt`, `--exclude`, and `TRASH_COMPACTOR_EXCLUDE`. This early cut avoids descending into areas that must never be touched. Dynamic high-entropy directory pruning during the walk itself is no longer performed for the main scan. The walk is fast enough that it is simpler and more accurate to discover candidates first and then apply entropy filtering to the collected set.

## Planning

The planner receives the stream of entries and builds the final list of work.

Classification for eligibility (extension, size, already-compressed) happens inside the Rust walker. The returned entries already carry the chosen algorithm, a category, and a size hint from `GetCompressedFileSizeW`.

### Algorithm Selection

Size thresholds decide the NTFS algorithm before any I/O:

- below 64 KiB: XPRESS4K
- 64–256 KiB: XPRESS8K
- 256 KiB–1 MiB: XPRESS16K
- 1 MiB and up: LZX (subject to the runtime benchmark that may disable it on slow CPUs)

This mapping is a simple cumulative threshold count. The executor later turns that integer into the right `/exe:` flag.

### Post-Discovery Entropy Filtering

After the walk finishes, DirectStorage trees are dropped before any entropy work. Presence of `dstorage.dll` or `dstoragecore.dll` (SteamDB and CompactGUI use the same marker) identifies a game root: the game folder in a Steam / Epic / Origin library, even when the DLL sits several directories deeper. Every candidate under that root is excluded from scanning. Remaining candidates are grouped by parent directory and entropy sampling runs on whole directories. Any directory whose projected savings fall below the configured minimum is dropped in bulk, together with all of its files.

A root-level entropy sample is also taken when the target directory itself contains compressible-looking files. The result can cause the entire run to be skipped early.

## Entropy Sampling

Entropy sampling decides, without writing anything and without reading every byte, whether compressing a directory tree is likely to be worthwhile. The implementation lives in a small Python wrapper and a high-performance reimplementation inside the Rust `fast_walk` crate.

File selection inside a directory is deterministic and biased toward impact: the walker collects candidate files, sorts them by descending size, and keeps only the largest N (default 50, controlled by `TRASH_COMPACTOR_ENTROPY_MAX_FILES`). Largest files dominate the potential space savings. Focusing the sampling budget there produces more reliable projections than uniform random sampling would.

For each chosen file a number of sample windows are read. The count is not fixed at three. Small files (2 MiB and below) receive the base of three windows. Larger files receive progressively more windows, scaling from four up to a hard maximum of twenty once the file reaches 100 MiB. The extra samples on big files reduce the chance that a large incompressible blob fools the estimator into thinking the whole directory is compressible. Each window is nominally 16 KiB. The implementation merges overlaps and respects a per-directory byte budget. Total I/O stays bounded.

Window placement for the three-window case targets roughly the 10 %, 45 %, and 80 % marks. This deliberately steps over the headers and trailers that many media and archive formats leave uncompressed. For files that use more windows the positions are spread evenly.

Each sample is first offered to LZ4. If LZ4 reports that the block is almost incompressible (ratio ≥ 0.95), the probe returns immediately with an entropy of 8.0 and marks the chunk as "certainly incompressible". Only when LZ4 does not short-circuit does the code fall back to zlib at level 2. Level 2 was chosen because it matches the compression style of the NTFS algorithms closely enough for good savings estimates while remaining fast. The weighted average entropy across the bytes actually read becomes the directory's score.

Directory probes themselves run in parallel through the Rust module. Rayon distributes the independent directory plans across threads. Inside each plan the per-file probes can also exploit parallelism for the larger jobs. Python only sees the aggregated scores. A serial path remains as a fallback for single-worker cases.

A persistent cache lets the program remember directories it has already declared high-entropy on previous runs. When a hit occurs the expensive sampling step is skipped entirely.

The average entropy value (0–8 bits per byte) becomes a projected percentage saving that the rest of the UI and reporting use.

## Execution

Once planning is complete the resulting list of files and algorithms is handed to the executor. Worker counts for compression are still chosen from the Python side according to CPU topology and drive type (see the concurrency notes). Discovery and entropy run in native code.
